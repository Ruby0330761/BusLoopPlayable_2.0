# Playable SOP

这份文档只保留真正高频、跨项目复用的执行顺序与实现规则。

## 默认顺序

1. 提炼玩法规则与限制。
2. 资源解耦并记录缺口。
3. 先做编辑器。
4. 先做 AppLovin 基线包。
5. 基于 AppLovin 扩其他平台。
6. 全平台人工验收并回写。
7. 最后做静态校验与 hardening / 混淆。

## 1. 玩法规则提炼

目标：先把游戏规则说清楚，不先写试玩运行时。

最少要明确：

- 一句话玩法
- 玩家输入方式
- 核心反馈方式
- 胜利条件
- 失败条件
- 必须继承的限制
- 可以简化的规则
- 当前先不做的规则
- 关键场景、Prefab、脚本、配置来源

如果用户给的是 Unity 工程，先跑：

```bash
python3 scripts/playable/find_unity_gameplay_entrypoints.py \
  --unity-root <unity-project-root> \
  --output <report.md>
```

这个脚本会随着 playable kit 一起安装到目标工程里。先跑它，再补读命中的高价值脚本、场景、Prefab、配置表。

没有把结论写进 `docs/project/playable-core-rules.md` 前，不要直接开始写最终试玩运行时。

## 2. 资源解耦

默认不自动从原工程抽取资源。

优先让协作者手动交付：

- 核心交互资源
- 背景和 UI 资源
- 关卡 / 玩法配置
- 音频资源
- CTA / 品牌素材
- 平台附加文件

目标是让 playable 工程和源工程解耦，而不是规定资源目录格式。

资源变化必须回写：

- `docs/project/playable-resource-status.md`
- `docs/project/playable-project-progress.md`

## 3. 编辑器优先

编辑器不是附属工具，而是主线。

原因很简单：AI 最容易做错的不是纯逻辑，而是：

- UI 布局
- 交互区摆位
- 路线和轨迹
- CTA 位置和节奏
- 引导节奏
- 难度和变量

所以必须先把给人类确认的控制面做出来，再做最终试玩页。

编辑器最低要支持：

- 场景或关卡切换
- 关键布局位置调整
- 关卡参数调整
- 引导和 CTA 配置
- 预览
- 场景导入 / 保存或等价的数据导出
- 打包入口和当前构建状态

## 默认技术建议

- `3D`：`Three.js + TypeScript`
- `2D`：`React + TypeScript`

这只是默认建议，不是硬约束。若目标工程已有成熟稳定栈，应优先跟随现状。

## 关键架构规则

- 编辑器、预览、最终 playable 必须共用同一份数据模型。
- 高频变化的场景数据不要直接绑进重型生产 bundle。
- 平台差异尽量只放在桥接层、导出层、规则层，不要复制多套玩法实现。
- 正式发布包和临时调试包要有清晰区分。

## 浏览器自动化

以下情况优先考虑浏览器自动化：

- 视觉布局问题
- 点击路径或 CTA 问题
- 最终包交互异常
- 音频触发时机异常
- 需要截图、录像或控制台证据

优先验证最终构建产物，不要只看 editor 或 dev server。
详细建议看 `docs/playable/browser-automation.md`。
