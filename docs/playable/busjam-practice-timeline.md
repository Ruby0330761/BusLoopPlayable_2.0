# BusJam Practice Timeline

这个时间线只保留对通用 playable SOP 有用的结论，不保留项目内细枝末节。

## 2026-03-27 重做起点

- 从现有 Unity 工程重新接手 playable，而不是在旧试玩工程上缝补。
- 很快确认最大坑不是“基本玩法能不能跑”，而是：
  - 停车区范围
  - 接驳区位置和尺寸
  - 队列位置
  - 发车路线
  - 上车站位
  - CTA 和最终 UI
- 直接结论：布局与 UI 相关内容必须先进入轻量编辑器，由人类把关。

## 2026-03-27 到 2026-03-30 编辑器主线

- 编辑器被证明是主线而不是附属物。
- 需要同时支持：
  - 场景导入和保存
  - 参数调节
  - 资源切换
  - 运行预览
  - 打包入口
- 关键经验：
  - 编辑器数据模型和最终 playable 运行时必须共用同一份场景数据。
  - 不要让预览逻辑和实际打包逻辑分叉。

## 2026-03-31 试玩态 UI 与 CTA

- 最终试玩页增加固定 CTA、引导、结束蒙层、音效和动态时机。
- 关键经验：
  - 试玩态 UI 不要继续暴露调试按钮。
  - 引导、CTA、结束态都要能在编辑器或配置里调，不要写死在代码里。
  - 最终交互的节奏属于投放变量，不只是“功能是否可用”。

## 2026-04-01 AppLovin 基线与 5MB 收口

- AppLovin 被确认为基线平台。
- 单文件、全资源内联、包体 <= 5MB 成为第一阶段的硬目标。
- 关键经验：
  - 验证优先看最终 `dist/index.html` 或正式导出物，不要只看 dev server。
  - 包体过大时，优先从资源策略下手，而不是先重构玩法层。
  - 浏览器自动化适合验证最终导出页的加载、点击、截图和运行状态。

## 2026-04-01 全平台扩展启动

- 启动 Google Ads、Meta、Moloco、Mintegral、TikTok、Unity、Liftoff 调研与适配计划。
- 关键经验：
  - 平台差异主要集中在交付格式、CTA API、生命周期、音频兼容和字段识别。
  - 不能照搬现成开源“跨平台 playable 打包器”，只能借鉴平台导出分层思路。
  - `Liftoff` 生命周期模型差异大，应默认延后。

## 2026-04-02 人工审查与平台特定问题

- 真实平台上传暴露的关键问题：
  - `Meta`：无声音
  - `Mintegral`：module/CORS/黑屏/结构不合规
  - `TikTok`：后台只识别 `Vertical`
- 关键经验：
  - 平台真实后台比静态校验更早暴露致命问题。
  - Meta 音频链路需要更保守的兼容方案。
  - Mintegral 对 classic 单 HTML 包和生命周期桥接更敏感。
  - TikTok 的 `config.json` 方向字段必须用真实后台结果校正。

## 2026-04-02 到 2026-04-03 文档与静态校验器回写

- 所有真实踩坑都被回写到：
  - 平台 audit 文档
  - 执行计划
  - 人工验收清单
  - 独立静态校验器
- 关键经验：
  - 真实修复结论必须回写成离线规则，不然团队会重复踩坑。
  - 静态校验器要随着平台结论演进同步更新。

## 2026-04-03 导出命名、批次目录与混淆接入

- 编辑器导出开始承担“正式发布”职责。
- 关键经验：
  - 打包状态必须单独展示，不要复用配置保存提示。
  - 导出目录、批次、文件命名要服务于投放和运营，不只是技术人员。
  - 正式导出与随手调试导出要清晰区分。

## 2026-04-06 打包性能根因

- 慢不是因为“全平台串行”，而是：
  - 场景数据被当成代码编入大 bundle
  - 每次改场景都触发完整生产构建
  - 每个平台再重复做重型后处理
- 最终解法是：
  - 让代码层构建缓存成发布模板
  - 每次打包只注入当前场景数据
  - 避免每个平台重复重建和重复混淆
- 关键经验：
  - 不要把频繁变化的数据塞进需要重构建的大 JS bundle。
  - 打包按钮应该吃“当前实时编辑状态”，而不是要求用户先手动保存。

## 对通用 Skill 的提炼

- 先理解规则，后做资源接入。
- 先做人类可控的编辑器，后做最终试玩页。
- 先做 AppLovin 基线，后做多平台。
- 先做真实平台人工验收，后做静态校验补漏。
- 最后才接混淆。
