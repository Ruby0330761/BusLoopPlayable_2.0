## 实施边界与研究纠正（2026-11-12）

- 直线距离 6.42 与绕行距离 13.44 只说明路线形状，不能证明错误：既有玩法要求车辆先沿车头方向驶出，直线可能穿过其他车辆。前轮把这一比较称为根因，证据不足。
- 原始数值探针中有几次把世界车位坐标直接传给要求源空间输入的函数；这些探针不作为验证依据。实际模型 `getSpotPosition()` 的结果才可与路径生成配合使用。
- Unity `spotYaw=0` 与编辑器 16° 是不同来源/坐标语义，不直接证明导出丢值。现有显式编辑器值继续优先，原生配置只补缺省，避免一刀切改掉已调好的车位。
- 未证明打包器丢失路径字段。已确认的是源空间边界手动固定、旋转后的逆朝向未补偿阵列旋转、终点采样浮点回跳，以及预览/派车没有显式配置快照。
- 当前默认构建有 `bl42-progress` 会话覆盖，使用 level15 / 6 车位；编辑器单关预览可为其他关卡 / 4 车位。方案 A 保留该会话选择语义，对每个实际 stage/choice 的有效配置分别烘快照，只有相同输入才比较路径一致性。
- 范围：新建 `src/vehicle-path-config.js` 与行为测试；接入模型、渲染、编辑器、旧 profile 迁移、导出生成器和导出入口；更新生成源码、版本及导航。无第三方增删、无远程发布。运行面为浏览器 Three.js + DOM 编辑器 / Node 构建，质量等级为核心运行行为回归。
- 优先级细化：当前编辑器/导出请求里的关卡调参（包括操作者的显式覆盖）> 原生 motion 的缺省 > 内建缺省；stage 车位数继续按已有会话契约覆盖。不能用原生值覆盖完整 editor tuning 快照。
- 旧 profile 没有 `autoBounds` 且四边不同于旧默认时，迁移到手动模式；新配置默认自动。自动计算完整旋转车身、容器轮廓和转弯留白，使用车位接近行衔接。派车捕获不可变配置及坐标变换平移量，渲染不再通过另一份实时全局调参解释该次运动。
- 验证：源/世界坐标和朝向双向变换；自动/手动与旧档兼容；逐车逐车位比较；生成 stage 快照和模型路径比较；100% 采样端点；既有模型/导出/缓存/体力回归；完整构建、单 HTML 打包、浏览器控件切换与 runtime 门禁。保留实际结果于本文实施结果及项目 progress。

## 结论摘要

前轮研究提出以下设计风险；根因强度和适用范围以上方实施复核为准：

1. 到站路径由固定矩形边界和“第一个空车位”共同推导，不读取每个车位的实际可通行空间，也不根据车阵或车位变化重新规划。
2. 运行时、预览和导出各自拼接全局调参与关卡数据，路径参数没有随关卡生成一个不可变的解析快照。
3. 完整关卡编辑器不显示车辆行驶路径；“显示路径”只存在于旧调参面板，而且默认关闭，导致编辑、预览、导出之间缺少可比对的中间证据。

数值复现基于当前默认调参：

- 起点 `(-0.1254, -2.4621)`，目标车位 `(-1.0179, 3.9000)`。
- 起点到车位直线距离约 `6.42` 源单位，当前生成路径约 `13.44` 源单位。
- 路线从起点到下边界，再沿右侧长边绕行，最后从上边进入车位；屏幕方向还受 Z 镜像影响。
- `LEVEL_1` 的 81 辆车全部位于当前全局矩形内部；配置边界为 `x [-3, 2.95] / z [-3.22, 2.82]`，而实际车阵约为 `x [-2.21, 2.23] / z [-2.46, 1.67]`。

当前 19 个可运行关卡带有 Unity 的 `spotStartX / spotZ / spotYaw`，但运行时优先读取全局 `SCENE_TUNING.facing` 与 `SCENE_TUNING.parkingSpots`。例如 Unity 车位的 `spotYaw` 为 `0`，编辑器全局默认是 `16`，两套数据同时存在。

## 当前运行链

```text
关卡编辑器车阵
  → 服务端保存关卡 / 本地 tuning profile
  → 运行时按全局调参和首个空车位生成路径
  → 预览线用同一算法
  → 导出时把 tuning 快照写入临时工作区
  → 单文件运行时解释路径
```

这里有两个不同坐标空间：

- 关卡车辆、车位、碰撞在作者的源空间。
- 渲染和路径预览最终经 `mapVehicleAreaPoint` / `mapMotionPoint` 转成 Three.js 世界空间。

路径构建函数接收的入口、边界和目标都在源空间；渲染时再统一映射。来源本身合理，但边界和目标没有通过一个显式的关卡路径快照固化。

## 关键代码证据

- `src/vehicle-motion.js`：`buildToStationPoints()` 用射线求出口，绕 `parkingBounds` 转向车位；`buildRoundedPath()` 对拐角统一做半径和双控制点圆角化。
- `src/game-model.js`：真正派车时读取 `SCENE_TUNING.vehiclePath`；目标车位在 `getSpotPosition()` 中用全局车位角度和首个空位计算。
- `src/scene-view.js`：编辑器预览同样调用 `buildToStationPoints()`，但只选择当前第一个空车位，逐车画模拟路线。
- `src/scene-tuning.js`：路径边界、转弯半径和车位角度均为全局默认。
- `src/level-catalog.js`：每个关卡有原生 `vehicleMotion`，但路径运行时没有以它为车的唯一来源。
- `src/level-layout-editor.js`：完整车阵编辑器没有绘制到站/离场路径，无法直接判断车阵修改会怎样改变路径。
- `scripts/export-playable-package.mjs`：导出把 tuning 写进临时工作区，并让关卡文件与 tuning 分开进入构建。

## 问题判断

### 1. 固定矩形绕行与真实空位不匹配

`buildToStationPoints()` 在矩形边界上找出口，再通过边界拐角进入车位。它不做可通行区域或障碍图判断，因此：

- 车阵中心的车可能被要求先冲出整个外围边界。
- 车位在边界内侧时，路径末端会出现“沿边横穿、再往回插入”的大绕行。
- 边界和车位接近时，圆角半径会被压缩，轨迹可能显著缩短或产生急转。

外围绕行本身符合既有规则；本次用自动包围轮廓和留白改善适配，不声称实现障碍寻路或最短路线。

### 2. 路径目标只按“第一个空位”，没有逐车位可行性评估

游戏派车时虽然按当前空位索引进入，但路径只需满足第一个空位；当车阵变化后，原本合理的车位可能变成不可达或路线别扭。编辑器预览也按第一个空位画一条统一样例，无法检查不同车种、不同起始点。

### 3. 全局 tuning 与关卡原生 motion 并存

Unity 关卡已有车位坐标/角度/接近方向，但运行时优先使用全局车位角度。`level5/12/26` 等关卡的原生 `spotYaw` 是 `0`，编辑器默认是 `16`；导出与预览只要有一个保存 profile 用了不同快照，车身终点朝向和进车位形状就会不同。

### 4. 预览与导出不是同一个“路径快照”

预览从当前浏览器 tuning 和空位画路径；导出传入经校验的 tuning，再由临时工作区重建场景。关卡文档中暂存 `tuning`，但目前 `levelDocumentToRuntime()` 只承载布局和 Unity 元数据，不把关卡文档里的路径调参作为运行时输入。

### 5. 完整关卡编辑器缺少路径可视化

车阵编辑器只显示车位安全框、车辆、容器和队列。路径线只在旧场景调参组里，默认关闭，并且画的是运行时当前状态的示意。车阵作者无法在拖车后看到“这条线会怎么变”，也无法在保存前发现“某辆车会绕整圈”。

## 方案 A：统一路径参数快照并派生边界（推荐先做）

保留现有的矩形绕行算法和 Unity 曲线时序，只消除数据不一致：

- 建立 `resolveVehiclePathConfig()`，输入关卡、调参和当前车位，返回不可变路径配置。
- `getSpotPosition()`、派车、预览和导出构建全部使用同一份解析结果。
- 明确优先级：关卡专属配置 > 关卡原生 `vehicleMotion` > 全局默认。
- 车位边界优先从车阵外轮廓和车位行推导，只有显式自定义时才使用固定边界。
- 把路径快照写入关卡文档或导出产物诊断字段，避免导出时再次读取另一份全局状态。

适用效果：消除坐标、朝向、边界与导出快照漂移，不会大幅改变现有的路径曲线形状。

风险：如果仍有其他层用全局调参，需逐个收敛；路径配置优先级一旦改动会影响现有保存档案。

改动范围：Level 1-2，D1，预计优先触及 `vehicle-motion.js`、`game-model.js`、`scene-view.js`、`level-editor-model.js` 和对应测试；不改打包器的主要职责。

验证：

- 同一车辆在不同入口、不同 token/profile 下，派车、预览和导出返回完全相同的路径采样。
- 边界随车阵和车位数量变化，不得依赖固定 `maxZ`。
- 现有 Unity 曲线和路径测试保持通过。

## 方案 B：按实际可通行空间做局部拓扑路径（推荐作为最终方向）

在方案 A 的解析快照上，把矩形边界替代为局部可通行区域或最小可通行图：

- 用车心 + 碰撞半径建立“进入车位可走区域”。
- 从入口到车位做一次确定性的 BFS/A* 或方向图搜索，优先最短、少转弯、少穿车行。
- 仍复用现有 `buildRoundedPath()` 的 Unity 转弯半径和曲线采样，使动画时序兼容。
- 在编辑器或导出诊断中保存/展示每辆车的搜索结果，并在无解时明确报错而非静默生成离谱线路。

适用效果：解决“直线只走 6.42 却绕 13.44”这类根因，路径看起来更自然，也能适应非矩形车阵。

风险：引入新的路径规划模块和缓存，需处理确定性、性能和不可达现象；现有路径测试不再足够，必须新增几何契约。

改动范围：Level 2，D2；分离为纯路径模块，由游戏模型调用，预览只消费结果。需要确认后才进入实现。

验证：

- 构造 4 个边界内车位和多种起始朝向，断言路径不穿墙、不穿过未让出的车位。
- 路径长度不超过“可绕行上界”，并在不可达时拒绝派车或给明确诊断。
- 与当前 Unity 派车动画对比时长、转向和终点朝向。

## 方案 C：改为显式路径作者模式（最大控制）

在关卡编辑器中为每个起始区/车位提供可编辑的路径控制点：

- 画面上直接显示、拖动和锁定路径控制点。
- 为每类车位或每辆车保存显式折线/曲线路径。
- 提供“自动生成 → 手动修正 → 下发到导出”的稳定流程。

适用效果：美术和策划可以逐条修正特殊车辆路线，适合少量、高定制关卡。

风险：所有关卡都要维护路径资产；车阵改动后手工路径会失效；路径容量和调试成本大，不适合作为默认路径来源。

改动范围：Level 3，D3，应单独立项，不应与本次通用路径修复一起做。

## 推荐顺序

1. 先做方案 A：统一解析和快照，将路径在编辑器、运行时、导出之间对齐。
2. 用方案 A 增加“路径诊断”开关和边界/目标/曲线的可视化证据，确认问题是否仍存在。
3. 若仍需修正“绕大圈”和复杂布局，再实施方案 B 的局部拓扑规划。
4. 方案 C 保留为特殊关卡的作者能力，不作为普通修复。

## 编辑器体验建议

- 在车辆面板加入“路径检查”视图，默认只显示当前选中车和第一个空位的完整路径。
- 视图里显示入口点、车位中心、停车边界、拐角半径、路径长度；点击某个车位可切换目标。
- 保存前验证路径：边界是否合理、车位角度是否来自关卡、是否存在不可达或异常绕行。
- 导出清单中增加路径诊断摘要，例如车辆数、平均路径长度、最大绕行比、异常车辆 id。
